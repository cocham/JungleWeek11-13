## 1단위 — 기본 저장·조회

**역할:** SQL 입력부터 디스크 저장·조회까지 전체 경로를 연결한다.

- 빌드·테스트 환경, CLI SQL 파일 입력과 여러 문장 순차 실행.
- INSERT, 전체 SELECT, users.tsv 저장과 읽기.
- 자동 ID, 재실행 시 데이터 유지와 다음 ID 복원.
- 기본 문법·컬럼·타입·범위 검증, fail-fast, 파일 오류 처리, 메모리 해제.
- 한글·작은따옴표·문자열 안 세미콜론 처리를 포함한다.
- WHERE는 아직 지원하지 않는다. 입력되면 오류로 거부한다.

**직접 확인:** 두 명 INSERT → 전체 SELECT → 종료 → 재실행해 같은 데이터 조회 → 세 번째 INSERT의 ID가 3.

**검증:** spec.md A1·A3·A4, A5~A8 중 이 단위 기능에 해당하는 사례. 파싱·저장 단위 테스트와 CLI 재실행 테스트, 사용 가능한 메모리 검사를 실행한다. 오류 처리를 2단위까지 미루지 않는다.

테스트 후 Codex 검증을 기다리며 멈춘다. 다음 단위를 자동 시작하지 않는다.

| `mingw32-make all build/test_unit.exe` | Windows, TDM-GCC 10.3 | 경고 0 |

| 직접 확인: examples/basic.sql → examples/third.sql | Windows | 재실행 후 기존 2건 유지, 세 번째 ID 3 |

LSan이 컨테이너에서 동작하는지는 일부러 누수를 만든 프로그램으로 확인했다(7바이트 누수 검출).
CLI 테스트는 모든 실행에서 stderr에 검사 도구 보고가 없는지도 확인한다.

## 2단위 — Phase 1 완성

**역할:** 조건 검색을 연결하고 전체 계약의 경계·실패 시나리오를 검증한다.

- WHERE id = 정수 / WHERE age = 정수. 둘 다 선형 탐색.
- 일치 없음·한 건·여러 건과 조회 순서 검증.
- 문법·숫자 범위·문자열 길이·손상 파일·I/O 실패 등 경계 검증 및 필요한 보강.
- 중간 문장 실패 시 앞선 저장 유지, 이후 문장 미실행 확인.
- 기존 테스트를 포함해 A1~A8 전체, 메모리 검사 재실행.

**직접 확인:** 같은 데이터에서 ID 검색·나이 검색 → 잘못된 SQL로 실패 확인 → 재실행해 저장 상태 확인.

테스트 후 Codex 검증을 기다리며 멈춘다. Phase 2는 시작하지 않는다.

**2단위 검증 기록(2026-11-13)**

| 명령 | 환경 | 결과 |
|---|---|---|
| `mingw32-make all build/test_unit.exe` | Windows, TDM-GCC 10.3 | 경고 0 |
| `mingw32-make test` | Windows | 단위 392개 검사 실패 0, CLI 28개 실패 0 |
| `docker run --rm -v "<프로젝트>:/src" -w /src gcc:13 make sanitize` | Linux, GCC 13.5, ASan/UBSan/LSan | 경고 0, 단위 392개 실패 0, CLI 28개 실패 0, 검사 도구 보고 없음 |
| 직접 확인: 3건 저장 → `WHERE id = 2`·`WHERE age = 25` → `WHERE age >= 25`가 든 SQL 실패 → 재실행 전체 조회 | Windows | 한 건·여러 건(저장 순서) 조회, 문장 2에서 실패, 앞선 INSERT 유지·뒤 INSERT 미실행 |

A1~A8 대응: A1·A3·A4는 기존 CLI 테스트, A2는 `a2_*` 5개, A5는 WHERE 오류 6건 추가, A6은 조회 뒤 실패, A7은 users.tsv 자리의 디렉터리·일치 뒤 손상 줄·stdout 쓰기 실패(`/dev/full`, Linux에서만 실행) 추가, A8은 위 표.

보강·점검 결과: 기존 오류·경계 처리(문법, 숫자 범위, 문자열 길이, 손상 파일, 파일 열기 실패)는 테스트로 확인했고 코드 변경이 필요한 결함은 없었다. 비교 연산자(`<` `>` `!`)는 "알 수 없는 문자" 대신 "'='만 지원" 오류가 나도록 Lexer 토큰을 추가했다.

남은 제한: 데이터 파일 쓰기 도중 실패(디스크 가득 참 등)는 자동 테스트로 재현하지 않았다. 코드는 fprintf·fflush 실패를 검사해 오류로 보고하며, 부분 기록된 줄의 복구는 spec대로 보장하지 않는다.

## 공통 검증·인계

- CLI 테스트는 실제 프로세스의 stdout·stderr·종료 코드·저장 파일을 확인한다. 임시 데이터 디렉터리를 쓴다.
- 경고를 활성화하고 지원 환경에서 ASan/UBSan 및 누수 검사를 실행한다. 실제 명령과 결과를 기록한다.
- 단위마다 변경 파일·테스트 결과·제한·실행 방법과 전체 흐름에서 맡는 역할을 짧게 전달한다.
- Codex 검증 이후 코드가 바뀌면 재검증한다.
- 커밋·푸시는 사용자 지시 후 해당 단위 변경만 작업 브랜치에 한다. main 직접 커밋·푸시 금지.
- 사용자에게 다음 단위 진행 지시를 받은 뒤 시작한다.

## 학습 순서

1. 1단위 결과물을 실행하고 SQL·출력·저장 파일을 비교한다.
2. INSERT 한 문장을 CLI → Parser → Executor → Storage 순서로 추적한다.
3. SELECT의 순차 읽기와 버퍼 소유권·해제를 확인한다.
4. 이해한 내용을 바탕으로 2단위의 조건 검색 설계에 참여한다.

학습 완료는 사용자가 판단한다. 함수별 학습 노트는 만들지 않는다.
