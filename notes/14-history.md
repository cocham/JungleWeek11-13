- 요구사항: R-P1-07(새 VDOM을 State History에 저장), R-P1-08(History의 VDOM으로 이동, 두 영역 함께 변경)

- 테스트: `tests/history.test.js`(모듈), `tests/phase1Page.test.js`의 "History 저장·이동"(페이지)

## 해결할 문제와 전체 역할
13번까지는 "앞으로만" 갈 수 있었다. History는 Patch로 반영한 화면을 VDOM으로 쌓아 두었다가, 과거 화면을 **다시 목표 화면으로 삼게** 한다.
되돌리기용 명령을 따로 만들지 않는다. 과거 VDOM을 꺼내 지금 VDOM과 diff하면, Patch와 똑같은 방법으로 바뀐 곳만 되돌릴 수 있다.

```
사용자 행동     데이터 변화                  원하는 화면              비교·반영                      실제 화면
Patch 클릭   → history.push(새 VDOM)      → 테스트 영역의 VDOM     → diff·patch                  → 바뀐 노드만
뒤로가기     → history 위치 -1            → 과거 VDOM(복사본)       → diff·patch + 테스트 영역 재생성 → 바뀐 노드만 되돌림
앞으로가기   → history 위치 +1            → 다음 VDOM(복사본)       → diff·patch + 테스트 영역 재생성 → 바뀐 노드만
```
- **Phase 1:** 과거 화면도 사람이 만들었던 "목표 HTML"의 VDOM이다.
- **Phase 2:** 상태가 바뀌면 컴포넌트가 새 VDOM을 계산한다. React는 이런 화면 기록을 자동으로 보관하지 않는다. History는 이 과제의 검증 도구다.

## 시나리오: 고치고, 되돌리고, 다른 길로 가기
```
로드            [v0]                    ●v0                   뒤로 ✕  앞으로 ✕
Patch(제목 A)   [v0, v1]                     ●v1              뒤로 ○  앞으로 ✕
Patch(항목 추가) [v0, v1, v2]                     ●v2         뒤로 ○  앞으로 ✕
뒤로            [v0, v1, v2]                 ●v1              뒤로 ○  앞으로 ○
   실제 영역: diff(v2, v1) → REMOVE 1개, 추가한 <li>만 떼어 냄. 제목 텍스트 노드 등은 같은 객체
   테스트 영역: v1로 새로 만듦 (Patch 안 한 편집이 있었다면 사라짐)
Patch(제목 B)   [v0, v1, v3]                     ●v3          뒤로 ○  앞으로 ✕   ← v2는 버려짐
```

## 정한 정책 (사람이 결정)

| 상황 | 동작 |
|---|---|
| 초기 화면 | 저장한다. 처음 화면까지 뒤로 갈 수 있다 |
| 과거 위치에서 새 Patch | 그 뒤(미래) 기록을 버리고 새 화면을 붙인다. 브라우저 뒤로가기·Undo와 같다 |
| 경계(맨 처음/맨 끝) | 버튼을 끈다. 상태 표시줄에 `(기록 2 / 3)`처럼 위치를 보인다 |
| Patch 안 한 편집 중 이동 | 테스트 영역을 이동한 화면으로 덮어쓴다 |
| 변경 없는 Patch·거부된 Patch | 기록하지 않는다. 같은 화면이 쌓이면 뒤로가기가 아무 일도 안 하는 것처럼 보이기 때문이다 |

## 단계별 입력·출력과 데이터 보관 위치

| 단계 | 입력 | 출력 | 보관 위치 |
|---|---|---|---|
| 로드 | `currentVdom` | 초기 스냅샷 | `history`의 `snapshots[0]` (깊은 복사) |
| Patch | 테스트 영역 VDOM | 반영 후 `currentVdom` | `history.push` → 지금 위치 뒤를 자르고 끝에 복사본 저장 |
| 뒤로/앞으로 | 위치 ±1 | 그 스냅샷의 **복사본** `target` | 지역 변수 |
| 이동 반영 | `currentVdom`, `target` | 실제 영역은 diff·patch, 테스트 영역은 `vdomToDom(target)` | `currentVdom = target`, `actualRoot` |

- 실제 영역은 Patch와 같은 `syncActual`로 맞춘다. Patch 버튼과 이동 버튼의 차이는 **목표 VDOM을 어디서 가져오는가**뿐이다.
- 테스트 영역은 다음 편집의 출발점이라서 diff하지 않고 통째로 새로 만든다. 테스트 영역에서는 노드 유지가 목적이 아니기 때문이다.

## 스냅샷 독립: 왜 복사하나
History에는 VDOM 객체를 넣는다. 같은 객체를 다른 곳과 공유하면 지금 고친 내용이 과거 기록에도 섞인다.
```
const v = domToVdom(...);  history.push(v);
v.children[0].text = '고침';        // 복사하지 않았다면 기록 속 과거 화면도 '고침'이 된다
```
그래서 `push`할 때와 `back`·`forward`·`current`로 꺼낼 때 모두 `cloneVdom`으로 깊은 복사한다. attrs 객체와 children 배열까지 새로 만든다.
지금 페이지 코드는 VDOM을 고치지 않고 매번 `domToVdom`으로 새로 만든다. 그래서 복사가 없어도 페이지 테스트는 통과하고, 복사를 빼면 `tests/history.test.js`의 독립성 테스트만 실패한다.
복사는 나중에 누가 VDOM을 고치더라도 과거 기록이 안전하도록 미리 막아 두는 장치다.

## 실제 DOM이 바뀌는 시점과 객체 유지
- **Patch:** 13번과 같다. 반영에 성공하고 patch가 하나 이상일 때만 기록한다.
- **이동:** 실제 영역은 diff 결과만큼만 바뀐다. 예) 글자 하나를 되돌리면 그 텍스트 노드의 값만 바뀌고, 주석과 다른 노드는 같은 객체로 남는다.
  루트 태그가 다른 기록으로 가면 실제 영역 안 같은 자리에서 루트가 교체되고, 새 루트를 `actualRoot`에 받아 둔다.
- 테스트 영역은 이동할 때마다 새 DOM이다. 실제 영역과 노드를 공유하지 않는다.

## 한계
- 기록 수에 제한이 없다. 오래 쓰면 스냅샷이 계속 쌓인다.
- 이동 도중 patch가 실패하면(diff 결과라면 일어나지 않아야 함) 위치는 이미 바뀐 상태로 오류만 표시한다. `currentVdom`은 실제 영역에서 다시 읽으므로 다음 비교는 어긋나지 않는다.
- 페이지를 새로 고치면 History는 사라진다(메모리에만 있음).
